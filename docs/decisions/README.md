- [ADR-0022](0022-stable-branch-promotion.md)（**Amended by ADR-0038**：提升必须额外绑定精确 dev SHA 的全量测试证据；当前命令面尚未实现该证据类型）：`dev → main` 稳定提升成为产品能力（`promotion prepare/approve/promote/restart.record/abandon/get/list`）。固定「被验证的 dev commit + 预期 main old OID + 集成验证证据」三元组，任一与事实不符即拒绝且不推进任何 ref；只有 `dev → main` 且只允许 fast-forward。FULL 零确认；STRICT 保留一次精确三元组批准，ref 或证据移动即 `STALE`。`main` 已被检出时在该工作树内 `git merge --ff-only <固定候选 OID>`，**禁止对已检出的 `main` 用 `update-ref`**；提升后由 CLI 客户端在执行 `main` 工作树内固定序列 `bun install --frozen-lockfile` → `bun run build:ui` → `bun run codeestra stop` → `bun run codeestra status`，只有「各步退出码 0 + 记账 Runtime 的 boot 与推动 main 的 boot 不同 + `status: READY`」才 `SUCCEEDED`（`uiRunning` 只记录为事实）；失败不回滚、保留现场，崩溃按 ref 事实 reconcile（不二次写 ref），不声称覆盖系统外手动更新 `main`。

- [ADR-0025](0025-runtime-lifecycle-stop-and-single-instance.md)：Runtime 生命周期可判定化。`codeestra stop` 改为「请求 + 有界等待 + 事实报告」（`STOPPED`/`NOT_EXITED` exit 0/1、`NOT_RUNNING` 不启动、`UNREACHABLE_PROCESS` exit 1 且**不杀进程**）；根因是各子系统把 `Bun.sleep(graceMs)` 放进 `Promise.race` 却从不清理 timer（Bun 会为 pending timer 保持事件循环，shutdown 跑完仍多活 ~5s），修复为清 timer 的 `withDeadline` + 顺序完成后确定性 `process.exit`（仅当没有未确认停止的 provider/验证进程）；启动改为 `runtime.lock`（硬链接原子写、`bootId/pid/startToken` 归属、owner 存活则拒绝、死后接管）+ 每次 boot 的 `runtime-boots/*.json` 痕迹，消除并发启动的双 Runtime、迁移崩溃与「socket 被并发启动者删除后不可达却永不退出」的竞态；新增只读诊断（CLI 直接读生命周期记录，不依赖 Runtime 存活、不写不删不发信号），自动回收不可达进程留待另立 ADR。
- [ADR-0029](0029-codex-adapter-transport-and-capabilities.md)：第二个真实 Adapter（Codex 0.151.0）接入。传输选 `codex app-server --stdio`（LF-JSONL JSON-RPC）而非 `exec --json`，因为只有它提供可承载 fail-closed gate 的审批应答通道、结构化提问、`turn/interrupt` 与 `thread/resume`；STRICT 复用 Codex 自己的 `untrusted` + `workspace-write` 审批策略并把请求映射到**既有** Attention 通道（FULL 则 `never` + `danger-full-access`，0 确认），不新增审批层。能力矩阵按实测填写：`cooperativeStop: REQUIRES_VALIDATION`（interrupt 不停已在跑的工具、杀 app-server 留孤儿）、`attach`/`reconnectToLiveSession`/`pause`/`revisionAcknowledgement: UNSUPPORTED`（Pi 的 ADR-0010/0023/0026 交接机制**不套用**）、`resumeAfterExit: SUPPORTED`（实测同 thread/同 rollout 路径）、新增 `controlledConfiguration: SUPPORTED|UNSUPPORTED`（Codex app-server 无 `--ignore-user-config`，ambient plugin/MCP/hook 参与执行）。interrupted turn 不产生 `completed` 证据（否则会写入假的 `toolsQuiescent`），改报 `disconnected`。记录未完成项：Runtime 目前没有 `FAILED → READY` 路径，因此「Execution 失败后换 Agent」只在 Execution 建立前失败或 pause→resume 路径上成立。

- [ADR-0028](0028-revision-delivery-and-stale-session-startup-reconcile.md)：修订投递确认与重启后 stale ACTIVE Session 的启动收敛（补齐 `## NEXT` 第 4 项）。投递是一等需求 + append-only 尝试台账（schema **v19**，只追加 `if (version < 19)`，v16 继续永久未使用）：**只有两个事实能满足它**——Adapter 返回带 evidence 的结构化 ACK，或停止后新建的 successor Execution 行被读回并确认 `applied_revision_id` 就是该 revision；「消息发出去了」永不当作确认。能力如实：`revisionAcknowledgement != SUPPORTED`、声明 SUPPORTED 但没有 `applyRevision` 端口、以及没有 evidence 的 ACK 分别记 `CHANNEL_UNSUPPORTED`/`UNACKNOWLEDGED`（Pi 仍 `UNSUPPORTED`，不声称热更新了规格）；不支持时唯一处置是既有「协作停止 + 新建 Execution」（`task revision delivery resolve --action stop-and-restart`，退出码 0 仅当确实满足），终止无法确认则 `RECOVERY_REQUIRED` 并保留现场；超时与重启中断的尝试按事实收口为 `TIMED_OUT`/`FAILED/RUNTIME_RESTARTED`，不自动重投。`reconcileStaleAgentSessions` 收敛 `agent_sessions`/`executions` 仍写 ACTIVE/RUNNING 的投影：按记录的 pid+start token 判所有权，**不写 RUNNING、不声称静止（进程树只是快照）、不发信号不杀进程、不删任何资源**，一律 `RECOVERY_REQUIRED` 并把观察值写进 append-only 台账与事件，幂等且不碰本代 Runtime 仍持有的 Session。命令面 `task revision create|list` 与 `task revision delivery list|get|resolve` 零确认、`--json`、退出码稳定。
- [ADR-0030](0030-phase2-parallel-scheduling.md)：Phase 2 并行调度的决策固化（纯文档，无代码、不占 schema 版本）。并发容量为**全局上限、默认 2、可配置**，并有**每 adapter 上限（默认等于全局上限）**，`wait(CAPACITY)` 区分 `GLOBAL_CAPACITY`/`ADAPTER_CAPACITY`；ImpactSnapshot 走**确定性规则 + 项目配置映射**（映射缺失 → `complete=false` → UNKNOWN → 不并行，不用 LLM 预测、不只靠文件路径+DAG）；调度由 Runtime **自动 tick**（事件驱动 + 周期恢复 tick）驱动，submit 后自动进入调度、FULL 0 确认；UNKNOWN 默认等待，新增**显式单次放行 `--allow-unknown`**（绑定 revision + `analyzerVersion`/`policyVersion`/`baseCommit`、写审计、**可与当前活跃任务并发**、不改变 assessment 记录、评估变化即失效；这是**放宽**而非新增门禁，常态路径 0 新增步骤，越界责任在放行方，Runtime 不做额外隔离）；**不加 aging**（只显示等待时长）、成果入 `dev` 继续**各自独立批次**、**不引入**非 Git 共享资源（端口/数据库/dev server）的 resource claim、影响映射载体是仓库内跟踪文件 `.codeestra/impact.json`（只从项目 main ref 读，读法同 `.codeestra/policies/verification.json`）；同时**逐字**修订 `PROJECT_SPEC.md` §2 不变量 6。Phase 2 代码未写，故「阶段进度」段落与本条均不得当作已实现。

- [ADR-0031](0031-impact-snapshot-and-deterministic-conflict-analyzer.md)：ImpactSnapshot 与确定性 Conflict Analyzer（Phase 2 的影响分析与保守冲突分析，schema **v20**）。影响范围来自仓库内跟踪文件 `.codeestra/impact.json`（读自 project `main` ref，Task 分支无法改写判定自己的映射），是**人工声明**而非推断：重要目录 / 模块 / 全局资源（含显式 `consumers` 读写依赖），路径按组件比较、拒绝绝对路径/`~`/`..`/`.git`/通配符/分离器逃逸，且这些路径从不被文件系统打开，所以 symlink 逃逸在结构上不可能。纯领域判定器（`packages/domain/src/impact-analysis.ts`，无 Bun/DB/Git/模型依赖）产出 `SAFE_TO_PARALLELIZE | UNKNOWN | CONFLICTING` 加稳定 reason code 与**具体命中范围**（相交路径/目录/模块/资源 + 关系）；映射缺失、非法、未确认、为空、全局效应不可界定、变更集超界一律 `complete=false` → UNKNOWN，活跃侧快照缺失/过期也一律 UNKNOWN——**不允许把「拿不到可靠信息」猜成 SAFE，本格不引入任何 LLM 判定**。存储 append-only：快照按 `(task, revision, base, analyzer, policy, change fingerprint)` 唯一、配对判定按两个快照唯一，任何事实变化写新行、旧行做审计，**永不覆盖**；迁移只追加 `if (version < 20)`（v16 永久未使用）。确认复用既有 `project trust` 事件：FULL 零步自动记录、STRICT 复用同一次 TRUST，**不新增确认或权限门禁**。命令面 `project impact validate|show|explain`（`--json`、稳定退出码；`explain` 退出码 0 仅当 SAFE）。**不含调度、容量、自动 tick 与多成员批次**（Wave F / E2）。

- [ADR-0032](0032-capacity-and-slot-reservations.md)：容量与槽位预留（Phase 2，schema **v21**）。容量是**配置**不是测量：项目级全局上限（默认 2，可配置）+ 每 adapter 上限（缺省 = 该项目的全局上限，派生而非复制），非法值（0/负数/小数/超上限/未知 adapter）以稳定码拒绝而不夹取。新增 `execution_slot_reservations` 表达 Task 执行权 + adapter slot + 可绑定的 workspace，两个部分唯一索引把「每 Task 一个活跃预留」「一个 worktree 不被两个活跃预留占用」变成 schema 事实；获取在 `BEGIN IMMEDIATE` 内重检 task 版本、revision、依赖事实指纹、容量（表内重读）与 draining，两次 tick/两个启动请求只能有一个成功。归属证据 = Runtime bootId + pid + OS start token（**不是**「这行是我建的」）；释放显式且带原因，绝不因心跳/等待/UI 消失自动释放，持有者可证明仍存活则拒绝释放。启动 reconcile 先核对真实写入者再决定：证明已死 → 记 `RELEASED`（`RECONCILED_HOLDER_EXITED`/`RECONCILED_PROCESS_ID_REUSED`），仍存活 → 保持占用，**无法核验 → `RECOVERY_REQUIRED` 保持占用、不自动放行**；观测写进 append-only 历史，幂等，不发信号、不删资源。容量等待用独立稳定码（`CAPACITY_GLOBAL_LIMIT_REACHED`/`CAPACITY_ADAPTER_SLOT_LIMIT_REACHED`/`SCHEDULER_DRAINING`）表达，`BLOCKED` 仍只表示依赖未满足。CLI `scheduler capacity get|set|clear` 与 `scheduler reservations list|get|acquire|release|prepare-workspace|reconcile`：零确认、`--json`、`acquire` 以退出码 3 报告容量等待。本格不含候选排序/自动 tick/`--allow-unknown`/非 Git 资源/impact 快照重检（Wave F 与 E1）；真实多任务并发执行与 provider 级槽位标为未验证。
- [ADR-0033](0033-scheduling-engine.md)：调度引擎（Phase 2，**未占 schema**，仍 v21）。把 E1 的判定与 E2 的预留接成真的会跑的循环：事件驱动 pass（submit/integrate/暂停/恢复/槽位释放/容量变更/执行结束/显式请求）会启动工作，周期恢复 pass 只收敛（刷新观测、检测越界、记录等待），Runtime 内 pass 互斥。候选顺序 priority desc → createdAt asc → id asc；逐候选依赖→冲突→容量→预留→workspace→启动前基线重检→启动一个主 Agent；冲突等待与容量等待各有稳定码且**都不是 `BLOCKED`**。一个从未启动过的候选没有 worktree，其观测改动集按**空集**经分析器自己的构造器产生预测（否则默认容量 2 退化为串行），残余风险由 §4 处置：以「启动时依据的那份预测」比对当前 worktree，越界且**可证明重叠**时写 `TaskImpactPredictionRevoked` 并经**既有协作暂停**请求该任务安全暂停（确认不了即 `RECOVERY_REQUIRED`），绝不抢占。自动 pass 只启动能证明 `SAFE` 的候选；显式 `task run` 在 `UNKNOWN` + 活跃集为空时可独占启动；`--allow-unknown` 是可审计的**单次**放行（绑定 revision/baseline/analyzer/policy 版本，落既有 append-only 事件台账，被一次启动消费，**不改写判定**，基线变化即失效），只放行 `UNKNOWN` 不放行 `CONFLICTING`。调度器的活跃集合按 `scheduler.md` §1 把仍持有 worktree 的 `PAUSED` 任务算进去（既有暂停实现会释放 `resource_held`，与 ADR-0031/0032 的文字不一致，已如实记录，容量口径未改）。新命令 `task schedule status|plan|explain|run|clear-unknown` 与 `task run|resume --allow-unknown`：零确认、`--json`、稳定退出码（0 启动 / 3 等待 / 1 拒绝），`task.run` 响应是既有结果的超集。未验证：真实 provider 并发、真实模型行为、UI 投影、多成员批次、非 Git 资源。
- [ADR-0037](0037-reclaim-batch-and-unregistered-directories.md)：`reclaim` 的跨项目批量与未注册目录的显式处置（FOUNDATION-062，schema **v24**）。`plan|apply|records` 用 `--project <id>` 或 `--all-projects`（省略 `--project` = 全部 ACTIVE-trusted project）选定作用域，批量端**每个项目一个独立 operation/receipt/账本行**（命令 ID 由批命令 ID 与 project ID 确定性派生），一条拒绝或失败不静默跳过其它条，聚合报告含 `projects[]` 分组、`operations[]`、`failures[]`。新增未注册目录（Runtime 数据目录里账本不认领的目录）：有界扫描（只走 `<home>/{worktrees,verifications,integrations}/<project-id>/<resource-id>`、两层、不跟 symlink、最多 500 候选、`--scan-root` 收窄到 home 内），判定依据随结果返回（路径形态 / 所属 home / `.git` 标记 / 账本认领 / Git 注册 / 工作区干净 / 进程表），**默认 dry-run**，只有 `--remove-unregistered <path>` 显式点名才删，删除前重核全部事实（Git 注册走既有 `removeOwnedWorktree`，未注册走窄 `rmSync`，都不删 branch、不 `--force`）；无法核验归属一律 `RECOVERY_REQUIRED` 且不删。账本同一本，schema v24 重建 `reclamation_records` 加 `source`、`UNREGISTERED_DIRECTORY` kind、`RECOVERY_REQUIRED` outcome、可空 `task_id`（既有行原样保留）。活跃槽位预留（`RESERVED`/`RECOVERY_REQUIRED`）与 held Execution 同级拒绝（`REFUSE/ACTIVE_RESERVATION`，`--include-failure-scenes` 不可越过）。**Amends ADR-0021 D03 的退出码**：0 = 有可回收项/确实回收了，3 = 正常 no-op（无可回收项），1 = 失败，2 = 用法错误。零新增确认。已知边界：无法归因到任何 ACTIVE-trusted project 的目录只报告不入账（账本是 project 作用域，凭空归因即假归因）。
- [ADR-0036](0036-task-retry-after-failure.md)：`FAILED → READY`：显式 `task retry` 与失败后换 Agent（Phase 5 缺口补全，schema **v23**——`executions.retry_from_execution_id` + `tasks.pending_retry_from_execution_id` 两列，无新表）。用户已拍板：**不自动重试**（不加次数/退避/loop/`--auto-retry`），只有显式命令让失败的 Task 回到调度；来源状态由纯领域判定给出稳定码 （`TASK_NOT_FAILED`/`TASK_CANCELLED`/`TASK_STILL_RUNNING`/`TASK_PAUSED`/`RECONCILE_REQUIRED`/`TASK_ARCHIVED`，拒绝不写任何行），目标状态由依赖判定重新导出（`READY` 或 `BLOCKED`）。新 Execution 由**同一条调度门禁**建立（`retry` 只 requeue，之后对该 Task 发一次 `runNow`）：容量/冲突等待是退出码 3 且 Task 留在 `READY` 排队，依赖未满足是 `REFUSED/DEPENDENCIES_UNMET`；`retry` 不提供 `--allow-unknown`（要放行先 `task run --allow-unknown`，沿用 ADR-0030 D05）。`--adapter` 缺省沿用该 Task 上次跑的 Adapter，换 Agent 即**新 Execution 绑定另一个 Adapter**，记为 `adapterChanged`/`previousAdapterId`；已知边界：若这次只得到 wait，后续由周期 tick 启动时用的是 Runtime 默认 adapter（引擎的 adapter 是整项目一个，本格不改引擎），`--json` 里 `adapterSource` 与 `start.outcome` 同时可见。worktree 优先复用该 Task 自己的，但**必须核验归属**（`reconcileWorkspace` 的 OWNED/MISSING/FOREIGN/UNCERTAIN → `REUSE_VERIFIED`/`PREPARE_FRESH`/`WORKSPACE_OWNERSHIP_UNVERIFIABLE`/`WORKSPACE_RECLAIMED`）：失败尝试留下的未提交工作不被丢弃，核验不了的 worktree 绝不交给新 Agent；**已 reclaim 的 worktree 被拒绝**——`reclaim` 不删 task branch，既有 preparation 路径会以 `REF_CONFLICT` 拒绝在既有分支上重建，该缺口如实保留、不引入第二套 Git 逻辑。旧 Execution 的失败、错误与证据原样保留（不重写历史、不伪造 RUNNING/RESULT）。未验证：真实 provider 失败后的重试、取消后重做（明确不做）、跨 adapter 复用历史 conversation、被 reclaim 后重建 worktree、`task retry` 的 UI 投影。

## ADR 规则
