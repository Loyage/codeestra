Codeestra / 项目导览面向新加入的开发者

不只让 AI 写代码，
让开发意图成为
可验证的工程成果。

Codeestra 是一个 Task-first、local-first 的 AI Development Runtime。它围绕任务组织 Agent、工作目录、依赖与验证，让软件开发不再依赖人手工维系的一组聊天窗口。

用户管理产品意图，Codeestra 管理软件工程。

建议讲解顺序：为什么做 → 如何工作 → 已经做到什么 → 如何参与。单文件、无外部资源，可离线阅读；使用浏览器打印可另存为 PDF。

01 /

从“与 Agent 对话”，到“管理开发任务”

要解决的不只是生成代码，而是从意图到稳定可用结果的工程协调成本。

THE PROBLEM / 今天的摩擦

写代码之外，还有大量人肉编排

任务交给哪个 Agent？两个任务会不会改到同一模块？上游“完成”后，下游是否真的拿到了代码？刚跑过的测试，验证的还是当前版本吗？重启之后，谁还在写工作目录？

如果这些答案只存在于聊天记录和人的记忆里，多开几个 Agent 窗口并不能自动带来可靠的并行开发。

THE VISION / 我们的方向

把工程关系变成系统能处理的事实

以 Task 表达目标，以 Revision 固定规格，以 Execution 记录尝试，以 Git commit 与验证证据定义成果。

长期愿景是把意图、依赖、执行、验证与稳定交付串起来；人专注产品判断，Runtime 承担可自动化的工程协调。愿景不等于这些环节已经全部自动化。

定位边界：不是聊天客户端，不是终端管理器，也不是套在多个 Agent 外面的 UI。它是本机单用户的开发编排服务；不以云端调度、多租户、分布式基础设施或桌面控制为目标。

核心区别：
左侧用户循环和右侧开发循环同时运行。用户不断产生的想法可以即时注入任务池；Codeestra 持续重算依赖并释放可执行任务。

03 /

三条第一原则

这是产品与工程取舍的最高依据，而不是可选的风格偏好。

01 — EFFICIENCY

效率至上

默认 FULL 主机级全权限，常态权限确认预算为 0 步、0 等待。可用 CLI 无确认切换 STRICT，恢复旧门禁。

减少用户等待，不用层层审批代替正确性核对。

02 — SERVICE + CLI

软件本体是服务

独立 Runtime 拥有业务语义；CLI 必须完备、可脚本化，提供机器可读输出与稳定退出码。

ADR-0067 起 Web UI 暂停，当前只启用 CLI/Unix socket。“只有 UI 能做”始终是缺陷。

03 — COMMAND-SURFACE TESTING

只从命令面验证

自动化测试与验收通过 CLI / Runtime Unix socket 命令面驱动；不获取用户电脑控制权。

不使用桌面、键鼠或真实窗口自动化；暂停的 Web UI/HTTP 不在当前测试范围。

零确认 ≠ 零校验，也不等于沙箱。FULL 下 Agent、验证命令和 Git hooks 使用当前系统用户的主机权限。Worktree 只隔离工作目录；revision、ref、归属、进程身份、幂等与恢复核对仍然有效。需要澄清产品意图时仍应提问，提问不是权限审批。
04 /

先记住这几个名词

Task 是业务主实体；Agent、Terminal、Conversation 和 Worktree 都围绕它服务。

Task要完成什么
一项有边界的开发工作，持有规格、约束、依赖、执行历史与验证状态。不是一条临时 prompt。
Revision哪一版要求
不可覆盖的规格快照。需求变化生成新 revision；旧版本的验证不能证明新要求已经实现。
Execution哪一次尝试
一次执行只绑定一个主 Agent。重试或换 Agent 产生新 Execution，旧失败和证据保留。
Session哪一个会话
有身份与生命周期的 provider 会话。不是无身份的 shell 调用；同一会话任意时刻最多一个 provider writer。
Worktree在哪里修改
运行中 Task 独占的 branch / 工作目录，从固定 dev commit 建立，位于 Runtime 数据目录。
Attention哪里需要人
提问、STRICT 权限请求或恢复介入。某个 Task 等待用户，不应让其他合格任务一起停下。
Verification凭什么算对
对固定 revision / commit 的验证记录；证据绑定 revision、commit 与策略 digest。合并后的集成验证已随 ADR-0066 删除。
成果 commit任务产出什么
固定在 refs/heads/task/<task-id> 上。是否合并、何时合并由你自己决定：产品不合、不推、不记账（ADR-0066）。
规格 → Revision   ·   尝试 → Execution   ·   成果 → Commit   ·   结论 → Evidence
05 /

一个任务，如何成为稳定成果？

下图是工程交付链，不代表一次命令就能自动完成整条流水线。

  1. 01 / INTENT

    明确意图与规格

    创建 Task，记录原始输入与首个 Revision。只有拆分能改善依赖、验证或并行边界时才拆分。

  2. 02 / SCHEDULE

    检查能否开始

    DAG 无环；上游结果已进入 dev；冲突与容量允许。UNKNOWN 不等于安全。

  3. 03 / EXECUTE

    隔离执行

    从固定 dev commit 建独占 worktree，预留 Execution，启动一个主 Agent 并记录 Session。

  4. 04 / CAPTURE

    固定成果 commit

    核对 revision、HEAD、ChangeSet 与写入静止事实。FULL 使用单步 capture，正常执行 Git hooks。

  5. 05 / VERIFY TASK

    验证这项改动

    在固定 commit 的 detached 副本跑已记录的定向计划，生成绑定 revision / commit 的证据。

  6. 06 / INTEGRATE

    独立验证后进 dev

    在 integration worktree 合并并独立验证；通过后才以 CAS 推进 dev。失败保留现场。

  7. 07 / HAND OFF

    成果交给你

    Task verification 通过后，成果停在 refs/heads/task/<task-id>：合并进哪条分支、什么时候合，都是你自己的 Git 决定（ADR-0066）。

  8. 08 / PROMOTE

    经远端进入稳定版

    远端 dev 核对 → main ff-only 拉取 → 稳定 Runtime 重启核对 → 最后推回 origin/main。

Agent 结束 ≠ 验证通过 ≠ 已进入 dev ≠ 已提升 main ≠ 稳定服务已恢复

示例：给导出功能增加新字段

如果 Task B 的导出逻辑依赖 Task A 的数据结构，A 的 Agent 说“完成了”不够，Task verification 通过也不够。A 的结果 commit 必须对 B 的固定基线可达——也就是你要把 A 合并进那条分支。

一个与它们无关的文档 Task C，只有通过影响与容量判断，才可能并行。这个例子说明设计规则，不代表真实 provider 并发已经验收。

运行中改变要求怎么办？

新增约束必须生成 Revision，并走暂停、投递与应用确认链。“消息发出去了”不是 ACK。

目前没有 Adapter 实现 applyRevision；不支持热投递时，走核验停止后新建 Execution 的路径，不能声称 Agent 已热更新规格。

当前边界：产品不再有集成与提升命令面。ADR-0066（schema v35）删除了 dev clone、长期 dev 集成分支、task integrate、task integration *、promotion * 与 dev 构建通道：Task 基线只有一种（项目文件夹建 workspace 时当前检出的分支），成果停在 refs/heads/task/<task-id>，合并由用户自己完成。docs/agents/runbook.md 里的人工四步只是本仓库自身的约定。

调度器不靠猜

影响映射来自 main ref 上的 .codeestra/impact.json。确定性分析产出 SAFE / UNKNOWN / CONFLICTING，不用 LLM 猜冲突。

自动调度只启动可证明 SAFE 的任务；UNKNOWN 可显式单次放行，CONFLICTING 不放行。依赖、冲突与容量等待分别表达。

恢复不靠盲目重试

SQLite、Git 与进程之间没有跨系统原子事务。先记录 Operation，再执行副作用，最后按可观察事实收口。

命令回执保证幂等，事件去重与 Outbox 支持可靠投递。进程状态无法核验时保留恢复态，不伪造成功。

知识不覆盖人工规范

人工 instructions / skills 进 Git，只从 main ref 读取；机器生成层只放 Runtime 数据目录，避免进入成果 commit。

每个 Execution 绑定知识快照与摘要；三个 Adapter 启动时会把绑定的物化文件注入 provider（Pi --append-system-prompt、Claude --append-system-prompt-file、Codex developer instructions，ADR-0051），但「模型真的读取并使用了它」仍待真实模型验收。

08 /

下一段路：补闭环，也补证据

不是推倒重来，也不是同时实施所有 Phase。下面按工作性质归纳，不是新增排期承诺。

A / Wave L 已落地

提升走完产品命令面

ADR-0047 已由产品实现（FOUNDATION-077 / ADR-0052）：push 固定候选 → 读回核对远端 dev → 等待 main 检出人工拉取 → 收口核对并重启 → 推回 origin/main。

“已推送、等待拉取”与“已提升”在命令面可区分。剩余边界：「等待拉取」的 UI 投影、多成员批次，以及全量证据仍从 main 检出读取候选。

B / 已有基础，补实现与验证

把能力声明变成证据

真实 provider 并发、暂停 / 恢复、取消超时、交接权限矩阵、第三方插件实际使用、Claude 模型层，以及知识注入后的模型层消费效果（注入已接通，ADR-0051）。

区分“协议通了”“进程退出了”“模型按预期工作了”，每一项单独证明。

C / 后续能力与设计边界

扩展而不伪造完成度

多成员 IntegrationBatch、Session Guidance、修订与投递的 UI 投影，以及后续 Self Evolution。

自我演化要先解决数据兼容、不可逆 migration 与 bootstrap 更新授权，不能把切二进制当成数据回滚。

长期方向：Codeestra 最终也能作为自己开发流程的编排者，但“现在用 Codeestra 辅助开发 Codeestra”不等于“自动自我升级已实现”。运行 Stable 与开发 Candidate 必须隔离。
09 /

新开发者需要守住的交付边界

快速推进的前提，是每一步都知道修改了什么、验证了什么、尚未证明什么。

先明确语义，再实现小步

  • 开工先读规格 §1.1、当前 ADR、任务记录，检查 Git 状态与已有改动。
  • 产品行为、公共 API、数据模型、Git 安全有重大歧义时，给选项并记录 ADR；未答复不等于批准。
  • 不把整条 roadmap 当作本次授权。普通局部、可逆的内部细节自行处理。
  • 完工同步 docs/tasks/，保留失败、未验证项与实际检查结果。

实现围绕不变量，而非界面效果

  • Domain 保持纯净；外部输入在 Zod 边界校验，引用与唯一性由数据库约束保护。
  • Git / 进程 / SQLite 的组合用可恢复步骤，不假装跨系统原子。
  • 命令使用参数数组；路径、ref 和进程归属必须核验，不依赖显示名称。
  • 不静默覆盖人工 instructions / skills / policies，不把密钥写进日志或提交。

本仓库自身的发布约定 / 不是产品能力

dev → origin/dev → main → 重启核对 → origin/main

这一节只适用于 Codeestra 自己这个仓库（ADR-0066 之后产品没有任何提升命令）。固定候选与预期 main SHA 后：

  1. 只 push 固定候选到远端 dev，并读回核对 SHA 相等。
  2. 在 main clone 执行 fetch + merge --ff-only origin/dev，核对拉到的就是候选。
  3. 在 main clone 按顺序 install → stop → status；只有 status: READY 才报告 Runtime 恢复。
  4. 重启核对成功后，才 fast-forward push main 回 origin/main。任一步失败就停下，保留现场，不擅自回滚或强推。

ADR-0067 起这里没有 UI 构建或启动步骤。完整命令序列见 docs/agents/runbook.md。

第一天：先确认你在运行哪一份代码

本机双 clone 布局是当前开发环境约定；其他开发者请替换为自己的对应路径。

MAIN / 稳定实例

~/Documents/codeestra

检出 main，用于稳定服务与日常使用。只按既定规程拉取、安装和重启；不在这里开发新功能，不复制 dev 未提交改动。

与 dev 不是彼此的 worktree，也不共享对象库、node_modules 或运行数据。

DEV / 开发实例

~/Documents/codeestra-dev

检出 dev，使用独立 CODEESTRA_HOME。当前只运行 CLI/Runtime；Web UI 已暂停。

区分开发与稳定实例依靠检出目录和 CODEESTRA_HOME。

# 使用 Nix 提供工具；以下示例在开发 clone 执行
nix shell nixpkgs#bun nixpkgs#nodejs_24 nixpkgs#just
cd ~/Documents/codeestra-dev
pwd
git branch --show-current
git status --short

# 每个 clone 都需要自己的依赖；Web UI 已暂停，无 UI 构建步骤
bun install --frozen-lockfile

# 仅为当前 shell 设置独立实例目录
export CODEESTRA_HOME="$HOME/.local/state/codeestra-dev"
bun run codeestra status
bun run codeestra settings permission get

这段命令会启动 dev Runtime，但不会创建任务或启动 provider 执行开发工作。当前没有 Web UI 地址、端口或 token。

最常见的误判：在 dev clone 执行不带独立 CODEESTRA_HOME 的 CLI，可能连接的是已经运行的稳定 Runtime，不能证明 dev 代码已生效。区分两个实例靠 CODEESTRA_HOME 与所在目录，界面上没有 dev 标记（ADR-0066 删除了它）。

讲解结束后，确认大家能回答这四个问题

为什么不是“一个 Agent = 一个任务”？

Task 表达目标与交付，Execution 表达一次尝试，Agent 是执行资源。换 Agent 不该丢掉任务身份、规格历史与失败证据。

为什么“Agent 已完成”不是成功？

Agent 结束只是一条观察事实。还需成果 commit 与 Task 验证；验证通过后成果仍停在 task 分支，合并由你自己完成（ADR-0066）。

为什么已经有并行调度，仍写“并发未验收”？

调度器与夹具下的测试证明了编排规则；真实 provider 的两个 SAFE 任务同时执行，是另一项必须单独完成的受控验收。

接到第一个开发任务后，先做什么？

读相关规格与 ADR，检查现有改动，明确本次获准范围、涉及的不变量和少量定向测试，再开始实现。不要为熟悉项目顺手实施下一阶段或运行全量测试。
